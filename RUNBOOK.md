# RUNBOOK: что делать, если сервис упал

Для дежурного, который видит сервис впервые. Каждый шаг — команда. В документе нет секретов:
пароли лежат в `.env` на сервере, **не** выводите его содержимое на экран.

**Подготовка** (из папки проекта на сервере):

```bash
export COMPOSE_FILE=compose.prod.yaml          # PowerShell: $env:COMPOSE_FILE="compose.prod.yaml"
```

Адрес сервиса ниже — `http://localhost:8000`; если проверяете с другой машины, подставьте адрес прода.

---

## 1. Сервис не отвечает

**Симптом:** `/` или `/health` не отвечают, пользователи видят ошибки.

1. Жив ли сервис: `curl -s http://localhost:8000/health` → должно быть `{"status":"ok"}`
2. Запущены ли контейнеры: `docker compose ps`
   (`app` не `running` или постоянно перезапускается → `docker compose up -d`)
3. Что в логах: `docker compose logs --tail=50 app`
4. Частые причины по логам:
   - `Field required` → не хватает настройки. Какие имена есть в `.env`:
     `cut -d= -f1 .env` (покажет только имена; нужны `GREETING`, `POSTGRES_PASSWORD`, `GHCR_IMAGE`, `APP_VERSION`).
     Добавьте недостающую и выполните `docker compose up -d`
   - `pull access denied` / `manifest unknown` → неверный образ или тег. Что запрошено: `docker compose config --images`.
     Исправьте `GHCR_IMAGE` / `APP_VERSION` в `.env`, при приватном пакете выполните `docker login ghcr.io`
   - ошибки подключения к базе → сценарий 2
5. Недавно был релиз? → **сценарий 3 (откат)**
6. Не помогло за 15 минут → эскалация: позвать владельца сервиса (**<ФИО, контакт>**)

---

## 2. База недоступна

**Симптом:** `/health` отвечает `ok`, но `GET /messages` и `POST /messages` возвращают 500.

1. Подтвердить проблему: `curl -s -o /dev/null -w "%{http_code}\n" http://localhost:8000/messages` → `500` означает, что беда с базой
2. Статус базы: `docker compose ps db` (должно быть `healthy`)
3. Принимает ли база подключения: `docker compose exec db pg_isready -U appuser -d appdb`
4. Что в логах базы: `docker compose logs --tail=50 db`
5. База остановлена → `docker compose up -d db`, дождитесь `healthy`, затем `docker compose restart app`
6. Проверить результат: `curl -s http://localhost:8000/messages` → список сообщений на месте

⚠️ Не выполняйте `docker compose down -v`: флаг `-v` удаляет volume `pgdata` вместе со всеми данными.
Убедиться, что данные на месте: `docker volume ls` (должен быть volume с `pgdata` в имени).

Не помогло за 15 минут → эскалация: позвать владельца сервиса (**<ФИО, контакт>**).

---

## 3. Откат на предыдущую версию

**Симптом:** после выката новой версии появились ошибки.

1. Какая версия запущена: `docker compose config --images`
2. Какие версии были: `git tag --sort=-v:refname` (предыдущая — второй тег сверху)
3. Вернуть предыдущую версию в `.env`: откройте `.env` и поставьте `APP_VERSION="v1.0.0"` (подставьте нужный тег).
   Одной командой на Linux: `sed -i 's/^APP_VERSION=.*/APP_VERSION="v1.0.0"/' .env`
4. Применить: `docker compose up -d`
5. Проверить: `curl -s http://localhost:8000/health` и `curl -s http://localhost:8000/messages`
   (данные на месте — база при откате не трогается)
6. Откат не помог → эскалация: позвать владельца сервиса (**<ФИО, контакт>**)

Откат кода безопасен, потому что изменения схемы базы в проекте только обратно совместимы
(колонки добавляются, не переименовываются и не удаляются).
